# Сервер, рейтинг и Telegram-бот

Рабочий production-бэкенд — [`server.js`](server.js): один Node-процесс раздаёт
статику игры, хранит SQLite-рейтинг и аналитику, проверяет heartbeat забегов и
держит Telegram long polling. `worker.js` и D1-файлы оставлены как legacy-
прототип Cloudflare и не должны считаться эквивалентом production API.

Требуется Node.js 22.13 или новее (`server.js` использует стабильный встроенный `node:sqlite`).

## Переменные окружения

```text
PORT=8080
HOST=127.0.0.1
STATIC_ROOT=/opt/uboost
DB_PATH=/opt/uboost/backend/data/uboost.db
BOT_TOKEN=...
BOT_ADMIN_IDS=123456789,987654321
BOT_ADMIN_USERNAMES=zdanovnik
RULESET_VERSION=2026-08-04-v1
ANALYTICS_RETENTION_DAYS=90
ALLOWED_ORIGIN=https://31.130.148.55
GAME_URL=https://31.130.148.55/
TELEGRAM_IP_FAMILY=6
```

`BOT_ADMIN_IDS` — числовые Telegram `chat_id`, которым бот разрешает
админ-команды и пересылает личные обращения участников. В список должны входить
только доверенные операторы: в сообщениях могут быть адреса доставки и другие
персональные данные. Без allowlist админ-функции не работают. Отправь боту `/id`,
чтобы узнать свой chat_id для добавления в allowlist.

`BOT_ADMIN_USERNAMES` — bootstrap-список администраторов без известного ID.
`zdanovnik` включён по умолчанию. При первом личном сообщении или `/start` бот
один раз закрепляет текущий username за фактическим числовым `chat_id` в SQLite.
Дальше права проверяются только по ID: переименование аккаунта не отнимет доступ,
а передача старого username другому человеку не передаст ему права администратора.
Чтобы отозвать bootstrap-доступ, задай `BOT_ADMIN_USERNAMES=` пустым (или убери
конкретное имя из списка) и перезапусти сервис. Сохранённое закрепление останется
неактивным и не даёт прав, пока username отсутствует в актуальном allowlist.

`TELEGRAM_IP_FAMILY=6` задан только на production VPS: его IPv4-маршрут до
`api.telegram.org` таймаутится, а IPv6 работает. В других окружениях переменную
можно не задавать — Node выберет маршрут автоматически.

### Админ-команды бота

Все доступны только авторизованным `chat_id`: явно заданным в `BOT_ADMIN_IDS`
или один раз закреплённым через `BOT_ADMIN_USERNAMES`.

| Команда | Что делает |
| --- | --- |
| `/top10` (`/admin`, `/contacts`, `/winners`) | Топ-10 по суммарной подтверждённой дистанции с кнопками открытия диалога. После выбора модератор пишет обычные сообщения, фото и документы. Добавь `--from YYYY-MM-DD --to YYYY-MM-DD` для произвольного периода UTC и при необходимости `--ruleset VERSION`. |
| `/stats` | Воронка за 7 дней: заходы → старты → забеги → шеры → CTA, уник. игроки, ср. дистанция, копирования промокода. |
| `/season` | Текущий `RULESET_VERSION`, окно доски, число забегов/verified/игроков. |
| `/export` | Контакты победителей в CSV. Поддерживает `--from YYYY-MM-DD --to YYYY-MM-DD`, `--ruleset VERSION` и `--top N`. |
| `/void <run_id>` / `/void player <playerId>` | Снять `verified` с забега или со всех забегов игрока (модерация; доска пересчитывается). |
| `/notify …` | Собрать рассылку поздравлений (см. ниже). Ничего не отправляет — только превью с токеном. |
| `/confirm <токен>` | Подтвердить и отправить подготовленную `/notify` рассылку (токен живёт 5 минут). |
| `/reply <@username\|id> <текст>` | Сразу написать одному участнику. Основной способ ответа — обычный Telegram Reply на пересланное обращение. |
| `/support` | Показать краткую инструкцию по операторскому чату. |
| `/dialogs` (`/inbox`) | Последние 10 участников, писавших в поддержку, с безопасной командой открытия диалога. |
| `/chat <@username\|id>` (`/open`) | Выбрать активного собеседника на 30 минут. Последующие тексты и вложения модератора идут ему без дополнительного Reply. |
| `/who` | Показать активного собеседника. |
| `/done` (`/close`) | Завершить активный диалог, чтобы исключить случайную отправку не тому человеку. |

### Переписка с участниками

Участник открывает личный чат с ботом и пишет обычное сообщение. Бот копирует
текст или вложение каждому авторизованному оператору и добавляет служебный
заголовок с именем, `@username` или Telegram ID. Оператор отвечает через Reply
на заголовок либо скопированное сообщение — бот доставляет ответ тому же
участнику. Поддерживаются текст, фото, документы, голосовые сообщения и другие
типы, которые принимает Telegram `copyMessage`.

Первый Reply автоматически делает этого участника активным собеседником на 30
минут. После этого оператор просто пишет боту следующие сообщения и вложения —
они уходят в тот же диалог, а успешная доставка отмечается тихой реакцией ✅.
Таймер продлевается после каждого ответа. Перед
переключением можно проверить `/who`, выбрать другой контакт через `/dialogs` и
`/chat <id>`, а после обсуждения доставки безопасно закрыть сессию через `/done`.

Маршруты Reply переживают перезапуск процесса и хранятся 366 дней. В SQLite
записываются chat/message ID, Telegram username, имя, время последнего контакта,
технические отметки доставки и антиспама. Сами тексты, адреса, фото и документы
в базу приложения не копируются. Неактивные операторские контакты и маршруты
удаляются через 366 дней. Групповые сообщения в поддержку не попадают. При
нескольких операторах обращение получают все, поэтому перед ответом стоит
проверить, не ответил ли уже коллега.

Повторно полученный после рестарта Telegram update не рассылается заново, если
его доставка уже записана. Явный Telegram `429` повторяется после полного
`retry_after`; неоднозначные timeout/`5xx` у `sendMessage`/`copyMessage` не
повторяются автоматически, чтобы уже принятый запрос не создал дубль. Один
участник может передать не более 12 сообщений в минуту, после чего получает одно
уведомление о паузе.

Чтобы начать диалог без входящего обращения, используй
`/reply <@username|id> <текст>`. Пользователь должен ранее открыть личный чат с
ботом; Telegram не разрешает боту первым писать человеку, который его не запускал.

Формы `/notify` (двухшаговые — сначала превью, потом `/confirm`):

- `/notify winners <N> [--from YYYY-MM-DD --to YYYY-MM-DD] [--ruleset VERSION] [текст]` — топ-N по суммарному пробегу за период UTC. Плейсхолдеры в
  тексте: `{alias} {rank} {score} {distance}`. Без текста — дефолтное поздравление.
- `/notify user <@username|id> <текст>` — точечно одному человеку.
- `/notify campaign <имя> [N] [--from YYYY-MM-DD --to YYYY-MM-DD] [--ruleset VERSION]` — кампания из `backend/campaigns/<имя>.json`
  (`message`/`parseMode`/`buttonText`/`buttonUrl`) топ-N победителям.

Безопасность рассылок: отправка идёт очередью с паузой (щадит лимиты Telegram);
получатели без `chat_id` (не нажимали `/start`) пропускаются; кампании
идемпотентны — один игрок не получит одно и то же поздравление дважды
(журнал `notifications_sent`). Для rolling-периода без явных дат ключ кампании
стабилен в пределах UTC-дня; повторное подтверждение в этот день не дублирует
рассылку. Точечные `/notify user` не журналируются и дублирование не блокируют.

### Подведение итогов без заранее заданных дат

Все забеги сохраняются append-only с серверным временем начала и окончания.
Период конкурса выбирается позже административной командой; обе даты трактуются
как календарные дни UTC включительно. Например:

```text
/winners --from 2026-08-01 --to 2026-08-07
/export --from 2026-08-01 --to 2026-08-07 --top 25
/notify winners 10 --from 2026-08-01 --to 2026-08-07 Поздравляем!
```

После будущей смены сезона добавь `--ruleset <старая-версия>`, чтобы повторно
посчитать или проверить исторический период. Для строк старой схемы, где не
было `started_at`/`ended_at`, миграция использует `created_at` как оценку обеих
границ — такие результаты не исчезают из исторического экспорта.

В итог попадают только `verified=1` забеги, целиком завершённые внутри периода.
Автоматического выбора или уведомления победителей по таймеру больше нет.

## Правила рейтинга

- Публичная соревновательная доска содержит только `verified=1`.
- Публичная доска и challenge-ссылки содержат только анонимный `publicId`, не
  внутренний `player_id`/Telegram ID. Исторические `ref` мигрируются без потери
  счётчиков.
- Изменение имени, старт/heartbeat и сохранение результата требуют подписанного
  Telegram `initData` либо браузерного секрета; в БД хранится только его HMAC.
- `run_id` уникален: повторный `/v1/scores` возвращает прежний результат и не
  увеличивает суммарный пробег.
- У игрока может быть только одна активная heartbeat-сессия; новая сессия
  навсегда снимает предыдущую с призовой проверки.
- Сервер считает покрытое heartbeat-время, ограничивает суммарную дистанцию
  реальной огибающей скорости/частоты бустов и сохраняет принятые и отклонённые
  отметки в `run_beats` для проверки лидеров.
- `RULESET_VERSION` начинает отдельный сезон после изменения баланса. Версию
  назначает сервер при старте забега; клиент не может записать результат в иной сезон.
- Игра сначала показывает топ-5, остальные загруженные строки раскрываются
  кнопкой.
- `notify-winners.mjs`, API и команды бота используют те же `verified` и
  `RULESET_VERSION`.

Heartbeat доказывает правдоподобный темп и мешает параллельной/грубой накрутке,
но не является полной серверной симуляцией. Перед денежными/ценными призами
верхние результаты всё равно нужно проверять по журналу `run_beats` отдельно.

## Проверка

```powershell
npm test
```

Помимо игрового harness запускается HTTP/SQLite integration-тест: verified-
доска, произвольные периоды, heartbeat-аудит, запрет параллельных сессий,
защита личности, отсутствие Telegram ID в публичном API, дедупликация `run_id`,
серверная версия правил, ETag и защита админ-команды.

После запуска production проверять:

```text
GET /v1/health
GET /v1/leaderboard?period=week&limit=25
GET /v1/dashboard
```

## Данные и приватность

Сырой Telegram `initData` проверяется в памяти и не сохраняется. В БД остаются
Telegram ID/username для определения и связи с победителями, игровые результаты
и события. Production-таймер ежедневно запускает `backup-db.mjs`, проверяет
копию через `PRAGMA quick_check` и хранит 30 последних снимков. Для защиты от
потери самого VPS дополнительно нужен внешний backup.

Промокод показывается только когда реальная скидка создана в биллинге и
`CONFIG.PROMO.code` заполнен. Пустой код скрывает блок в игре, карточке и боте.
